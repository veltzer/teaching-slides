# The IO Subsystem

---

## How Does I/O Work?

1. When a process calls `read(2)` or `write(2)`, it triggers a system call, trapping into the kernel.
1. The kernel then interacts with the hardware (e.g., a disk controller) to perform the data transfer.
1. This process involves multiple layers of abstraction and caching to improve performance and manage hardware complexities.
1. Two key components in this process are the page cache and the buffer cache.

---

## The Kernel Page Cache

1. The page cache is the main disk cache used by the `Linux` kernel.
1. When you read from a file, the kernel fetches the data from the disk in page-sized chunks (typically 4KB) and stores it in the page cache (RAM).
1. Subsequent reads of the same data can be served directly from RAM, which is orders of magnitude faster than reading from disk.
1. This is why the second `cat` of a large file is much faster than the first.

---

## The Page Cache and Writing

1. When you `write(2)` to a file, the data is typically written to the page cache first, not directly to the disk.
1. The kernel marks these pages as "dirty."
1. The `write(2)` call can return immediately, giving the application the illusion of a very fast write.
1. The kernel writes the dirty pages to the disk at a later, more opportune time. This is called a **writeback** cache.

## Buffer Cache

1. Historically, the buffer cache was a separate cache for block device I/O.
1. It cached file system metadata (like superblocks and i-nodes) and data blocks.
1. In modern `Linux` kernels, the page cache and buffer cache have been unified.
1. The page cache now handles caching for both file data and block device data. The term "buffer cache" now loosely refers to the part of the page cache that holds metadata.

---

## Controlling I/O Priority with `ionice(1)`

1. The `ionice` command and `ionice(2)` system call can be used to set the I/O scheduling class and priority for a process.
1. This influences how the kernel allocates I/O bandwidth to different processes.
1. **Classes:**
    - `Idle`: Get I/O time only when no other process needs it.
    - `Best-effort`: The default class. Priority is based on the process's CPU `nice` value.
    - `Realtime`: Get first access to the disk, regardless of other processes.

---

## The Data Copy Problem

1. A standard `read(2)` involves at least two copies:
    1. Disk -> Kernel Buffer (Page Cache) via DMA.
    1. Kernel Buffer -> User Space Buffer via CPU.
1. A standard `write(2)` is similar:
    1. User Space Buffer -> Kernel Buffer (Page Cache) via CPU.
    1. Kernel Buffer -> Disk via DMA.
1. The copy involving the CPU consumes CPU cycles and pollutes CPU caches. For high-performance applications, this is a significant overhead.

---

## Overcoming the Copy Problem with `O_DIRECT`

1. Opening a file with the `O_DIRECT` flag attempts to bypass the page cache.
1. Data is transferred directly between the user space buffer and the disk.
1. This can improve performance for applications that do their own caching (like databases).
1. **Pitfalls:**
    - I/O must be aligned to file system block boundaries (in terms of buffer address, size, and file offset).
    - Can be slower if not used correctly, as it loses the benefit of the page cache.

---

## Overcoming the Copy Problem with `mmap(2)`

1. As discussed in the previous chapter, `mmap(2)` maps a file into the process's address space.
1. The kernel's page cache serves as the direct backing for this memory region.
1. When you read from the mapped memory, you are reading directly from the page cache.
1. This eliminates the explicit copy from kernel space to user space required by `read(2)`.

## Chapter Summary

1. We examined how I/O requests are handled by the kernel.
1. We learned about the crucial role of the unified page/buffer cache in improving performance through caching.
1. We saw how `ionice` can be used to manage I/O priorities between processes.
