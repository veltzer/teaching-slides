# OAuth2 Basics

---
## What This Chapter Covers

- The OAuth2 protocol shape
- Endpoints: authorize, token, revoke
- Scopes
- Client types and registration
- Redirect URIs

---
## The Big Picture

- A delegated authorization protocol
- Client gets a token from the auth server
- Client uses the token to access the resource server
- User consents in the middle
- Tokens encode (or reference) the granted permissions

## Standard Endpoints

- `/authorize` — where users land to grant consent
- `/token` — where clients exchange codes/credentials for tokens
- `/revoke` — to invalidate a token
- `/introspect` — to check if a token is still valid
- `/.well-known/openid-configuration` — discovery (OIDC)

---
## Standard Endpoint Roles

![standard_endpoints](svg/courses/networking/oauth2-and-oidc/02_oauth2_basics/standard_endpoints.svg)

---
## The Authorize Endpoint

- The user's browser is redirected here
- The auth server authenticates the user
- The user sees a consent screen
- After consent, redirects back to the client
- Standard query parameters: `client_id`, `redirect_uri`, `scope`, `state`

---
## The Token Endpoint

- Server-to-server (no user interaction)
- The client trades something (code, refresh token, credentials) for an access token
- Authenticated with client credentials
- Returns JSON: access token, optional refresh token, expiration
- Always over TLS

---
## Scopes

- Strings that limit what a token can do
- Examples: `read:profile`, `write:posts`, `admin`
- Requested by the client; user consents per scope
- Issued tokens carry the consented scopes
- Resource server enforces them

---
## Scope Best Practices

- Use specific scopes, not blanket "all access"
- Group by resource and action: `resource:action`
- Document each scope clearly for users
- Match consent UI to user mental model
- Don't pile on scopes — least privilege

---
## Client Types

- Confidential — can keep a secret (server-side apps)
- Public — cannot keep a secret (SPAs, mobile, native)
- Different security guarantees and grant types per type
- Older spec called native clients confidential — wrong; they are public
- Choose grants based on client type

---
## Confidential Clients

- Have a client secret stored securely server-side
- Web apps with backend, server-side jobs
- Use client_secret_basic or client_secret_post for token endpoint
- Can use stronger flows (client credentials, etc)
- Most powerful trust posture

---
## Public Clients

- Cannot store secrets safely
- SPAs, mobile apps, desktop apps
- Use PKCE to compensate for the missing secret
- Authorization code with PKCE is the modern recommendation
- Implicit flow is deprecated for public clients

---
## Client Registration

- Register your app at the auth server
- Get a client_id; possibly a client_secret
- Configure redirect URIs, allowed scopes, grant types
- Static or dynamic registration (RFC 7591)
- Misconfiguration here causes most production bugs

---
## Redirect URIs

- Where the auth server sends the user back after consent
- Must match exactly what was registered
- Critical security boundary
- Wildcards are dangerous; avoid
- Use HTTPS in production; localhost OK in dev

---
## Redirect URI Validation

- Exact match against registered URIs
- Case-sensitive in many implementations
- No `?` or `#` shenanigans
- One small mistake = open redirect / token theft
- Worth testing thoroughly

---
## The State Parameter

- Random opaque value generated by the client
- Sent on `/authorize`, returned by the server
- Verified on the redirect back
- Prevents CSRF on the authorization endpoint
- Always use it

---
## A Tiny Walkthrough

- User clicks "Connect to App"
- App redirects to `/authorize?client_id=...&redirect_uri=...&scope=...&state=xyz`
- User logs in and consents
- Auth server redirects back with a code and the same state
- App exchanges code for tokens at `/token`

## Bearer Tokens

- Whoever has the token can use it
- Like cash in your wallet
- Sent in `Authorization: Bearer xyz` header
- Always over TLS
- Short lifetimes mitigate theft

---
## Token Lifetimes

- Access tokens: minutes (5-60 typical)
- Refresh tokens: hours to weeks
- ID tokens: same as access typically
- Shorter is more secure but more refresh churn
- Match to your threat model

---
## Discovery

- `.well-known/openid-configuration` document
- Lists all endpoints and supported features
- Clients can configure dynamically
- Auth server changes propagate cleanly
- OIDC standard; OAuth2-only providers may not have it

---
## TLS Requirements

- Every endpoint must be HTTPS
- Tokens in plaintext over the network = catastrophic
- Some flows fundamentally require TLS for security
- No exceptions in production
- Local development with `localhost` is the exception

---
## CORS Considerations

- Token endpoint may need CORS for SPAs
- Authorization endpoint is browser-redirect, not fetched
- Resource servers need CORS for SPAs that call them
- Configure allowed origins explicitly
- Don't `*` for token endpoints

---
## Common Pitfalls

- Loose redirect URI matching (open redirects)
- Storing tokens in localStorage where XSS finds them
- Long-lived access tokens
- Skipping the state parameter
- Treating OAuth2 as authentication

---
## Summary

- Authorize endpoint for user consent; token endpoint for code exchange
- Scopes limit token power; least-privilege them
- Confidential vs public clients drive grant choice
- Redirect URIs and state parameter are security-critical
- Bearer tokens — keep them short-lived and over TLS
