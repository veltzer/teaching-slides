1Overview

Cloud Foundry (CF) is an opinionated application platform: you hand it source code and it does the rest. Kubernetes (k8s) is a general-purpose container orchestrator: you hand it containers plus a precise description of how they should run, and it makes reality match that description.

Application platform · PaaS

Cloud Foundry

  • Born at VMware in 2011, later Pivotal; now a Cloud Foundry Foundation project under the Linux Foundation.
  • Core promise: cf push and your app is built, packaged, scheduled, routed, logged and health-checked.
  • Buildpacks turn source into a runnable image; you never write a Dockerfile.
  • Strong multi-tenancy model: orgs, spaces, quotas, roles out of the box.
  • Modern distributions (Korifi, cf-for-k8s lineage) run on top of Kubernetes.
Container orchestrator · CaaS

Kubernetes

  • Open-sourced by Google in 2014, based on Borg; graduated CNCF project and de-facto industry standard.
  • Core promise: declare desired state in YAML; controllers reconcile the cluster toward it continuously.
  • Runs any OCI container: web apps, batch jobs, databases, ML pipelines, network functions.
  • Everything is an extensible API object; a vast ecosystem fills the gaps (Helm, Istio, ArgoCD, Knative…).
  • Available from every cloud (EKS, GKE, AKS) and on-prem (OpenShift, Rancher, k3s).
The one-sentence summary. Cloud Foundry optimises for the developer who wants to ship a twelve-factor app and never think about infrastructure. Kubernetes optimises for the platform team who wants a universal substrate on which to build whatever is needed.

2Philosophy: opinions vs primitives

The deepest difference is not technical but cultural. Cloud Foundry ships with a strong opinion about what an application is: a stateless, horizontally scalable process that speaks HTTP, reads configuration from the environment, and logs to stdout. If your workload fits that shape, CF removes almost every decision from your path. If it does not, you fight the platform.

Kubernetes refuses to have that opinion. It offers primitives (Pods, Services, Volumes, Jobs, ConfigMaps) and lets you compose them. The price is that somebody has to hold the opinions: which ingress controller, which secrets store, which CI pipeline, which observability stack. In a mature organisation that somebody is a platform team building an internal developer platform (IDP). In a small team it is often nobody, and the YAML sprawls.

Same shape, different scope. Both are API-driven control planes with a scheduler, node agents and a state store. The difference is that Cloud Foundry bundles the router, log pipeline, identity and build system as first-class parts of the control plane, while Kubernetes leaves them to add-ons.

4Developer experience

The clearest way to feel the difference is to deploy the same small web app on each.

Cloud Foundry

manifest.yml

applications:
- name: hello
  memory: 256M
  instances: 2
  buildpacks:
  - python_buildpack
  services:
  - hello-db

Deploy, scale, inspect:

$ cf push
$ cf scale hello -i 4
$ cf logs hello
$ cf create-service postgres small hello-db
$ cf bind-service hello hello-db

Route, TLS, health check, logs and the credentials in VCAP_SERVICES all appear with no further configuration.

Kubernetes

Dockerfile + at least three manifests:

apiVersion: apps/v1
kind: Deployment
metadata: { name: hello }
spec:
  replicas: 2
  selector: { matchLabels: { app: hello } }
  template:
    metadata: { labels: { app: hello } }
    spec:
      containers:
      - name: hello
        image: registry/hello:1.4.2
        resources:
          limits: { memory: 256Mi }
        readinessProbe:
          httpGet: { path: /healthz, port: 8080 }
--- plus Service, Ingress, Secret, HPA,
    and a database wired in by hand.

Deploy, scale, inspect:

$ docker build -t registry/hello:1.4.2 . && docker push …
$ kubectl apply -f k8s/
$ kubectl scale deploy/hello --replicas=4
$ kubectl logs -l app=hello -f

Neither approach is wrong. The Kubernetes version is more verbose because it is more explicit: every decision the CF buildpack and router made silently is now visible and changeable. Teams that need that control love it. Teams that just want the app running see it as ceremony. Tools like Helm, Kustomize, Skaffold, Tilt and Knative exist precisely to shrink this gap, at the cost of yet another layer to learn.

6Operating the platform

Developer experience is where Cloud Foundry shines. Operations is where the trade-offs get interesting.

Installation and upgrades

Classic Cloud Foundry is deployed with BOSH, which manages the full VM lifecycle including OS images (stemcells). Upgrades are a well-rehearsed, mostly rolling process, but BOSH itself is a large, unfamiliar tool with a small community. A full CF foundation is heavy: dozens of VMs before the first app is pushed.

Kubernetes is available as a managed control plane from every cloud, which removes most of the installation burden. On-prem, tools like kubeadm, Cluster API, Rancher, Talos and OpenShift cover it. Upgrades are frequent (three minor releases a year, each supported for roughly fourteen months), and each one can break API versions or add-ons, so operators spend real effort staying current.

The convergence story. The CF community responded to Kubernetes rather than fighting it. Korifi reimplements the Cloud Foundry API as Kubernetes CRDs and controllers, using Cloud Native Buildpacks (kpack) and Contour, so cf push works against an ordinary cluster. Cloud Native Buildpacks themselves are a CNCF project born from CF and Heroku buildpacks. Meanwhile projects such as Knative, Backstage and various internal developer platforms rebuild the "just push code" experience on Kubernetes from the other direction. The two worlds are meeting in the middle.

7Strengths and weaknesses

Cloud Foundry

Strengths

  • Fastest path from source to running, routed, logged application.
  • Developers need to learn one command and one small manifest.
  • Strong guardrails: consistent security, no root, patched runtimes, quotas.
  • Multi-tenancy and RBAC that match how enterprises are organised.
  • Service marketplace makes backing services a one-liner.
  • Proven at scale in regulated industries (banks, insurers, government).

Weaknesses

  • Opinionated: stateful, non-HTTP or unusual workloads fit badly or not at all.
  • Heavy footprint and BOSH learning curve for the classic distribution.
  • Shrinking community and vendor pool; hiring is harder every year.
  • Limited extensibility; if the platform lacks a feature you wait for it.
  • Less momentum in tooling and integrations than the CNCF ecosystem.
  • Perceived as legacy, which affects buy-in regardless of technical merit.

Kubernetes

Strengths

  • Runs every kind of workload on every kind of infrastructure.
  • Declarative API is a natural fit for GitOps and infrastructure as code.
  • Unmatched ecosystem: meshes, operators, observability, policy, ML, serverless.
  • Managed offerings from every cloud reduce the operations burden.
  • Largest talent pool and knowledge base in the industry.
  • Extensible to the core; you are never blocked waiting for upstream.

Weaknesses

  • Steep learning curve; developers must understand infrastructure concepts.
  • Verbose configuration; an app needs many YAML objects to be production-ready.
  • No batteries included: ingress, logging, secrets, CI must all be chosen and assembled.
  • Frequent releases and deprecations create ongoing upgrade toil.
  • Easy to build an insecure or unreliable cluster; many defaults are permissive.
  • Complexity tends to leak upward to application teams unless a platform team absorbs it.

8Choosing between them

The honest answer in 2026 is that most new platforms are built on Kubernetes, and the real question is which developer experience you put on top of it. Cloud Foundry remains an excellent answer where it is already installed, where the workload shape fits, and where the organisation values guardrails over flexibility.

Lean towards Cloud Foundry when…

  • Your fleet is mostly stateless web services and APIs.
  • You want developers to never see a Dockerfile or YAML.
  • Compliance requires strong, uniform guardrails across hundreds of teams.
  • You already run CF and it is meeting your needs.
  • A single vendor with a supported, integrated product is preferred.
  • You can run Korifi and get both CF ergonomics and a Kubernetes substrate.

Lean towards Kubernetes when…

  • Workloads include stateful services, batch, ML, GPUs or anything unusual.
  • You want one substrate for everything, including third-party software.
  • GitOps and declarative infrastructure are part of your culture.
  • You have (or will build) a platform team to curate the stack.
  • Hiring, community and long-term ecosystem momentum matter.
  • You are starting fresh with no existing platform investment.

A pragmatic middle path

Treat Kubernetes as the operating system and buy or build the application platform on top. Options in rising order of effort: a managed PaaS-on-k8s (OpenShift, Tanzu Application Platform), an open-source layer (Korifi, Knative plus Cloud Native Buildpacks), or a bespoke internal developer platform stitched from Backstage, ArgoCD, Crossplane and Helm. Whatever you pick, the goal is the same one Cloud Foundry set in 2011: a developer should be able to push code and walk away.

9Glossary

BOSH
Cloud Foundry's tool for deploying and managing the platform's own VMs across any IaaS.
Buildpack
A script set that detects an app's language, installs dependencies and produces a runnable image. Now standardised as Cloud Native Buildpacks.
CNCF
Cloud Native Computing Foundation, home of Kubernetes, Prometheus, Envoy, Buildpacks and many more.
CRD
Custom Resource Definition; the mechanism for adding new object types to the Kubernetes API.
Diego
Cloud Foundry's container scheduler and runtime layer.
Droplet
The staged, ready-to-run artefact a buildpack produces from source in Cloud Foundry.
Gorouter
Cloud Foundry's built-in HTTP router that maps routes to app instances.
HPA
Horizontal Pod Autoscaler; scales Kubernetes replicas on metrics.
IDP
Internal Developer Platform; an organisation's curated, self-service layer over raw infrastructure.
Ingress
Kubernetes object describing external HTTP routing; requires a controller to act on it.
Korifi
Cloud Foundry's Kubernetes-native reimplementation, exposing the CF API as CRDs.
Loggregator
Cloud Foundry's log and metric streaming subsystem.
OCI image
The standard container image format consumed by Docker, containerd, Kubernetes and Cloud Foundry alike.
Operator
A Kubernetes controller that manages a complex application (often stateful) using CRDs.
Org / Space
Cloud Foundry's two-level tenancy hierarchy for grouping apps, users and quotas.
Pod
The smallest deployable unit in Kubernetes: one or more containers sharing network and storage.
Service broker
An Open Service Broker API implementation that provisions and binds backing services in CF.
Twelve-factor app
A methodology for building portable, stateless, config-from-environment services; the workload shape CF was designed for.
UAA
User Account and Authentication; Cloud Foundry's OAuth2 identity server.
