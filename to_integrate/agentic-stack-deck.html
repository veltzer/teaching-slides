The Agentic Stack

Context windows, tools, MCP, agents, skills, plugins, and Claude configuration — the seven layers that turn a language model into a working system.

contexttoolsmcpagentsskillspluginsconfig

Navigate with ← → or the arrows below. 50 slides.

Why this map

A model alone answers questions. A system does work.

  • The model is the engine, not the vehicle. Raw LLMs are stateless text-in, text-out functions. Everything useful around them is engineering.
  • Every production AI app answers the same questions. What does the model see (context)? What can it do (tools)? How does it connect to the world (MCP)? How does it work autonomously (agents)? How does it learn procedures (skills)? How is it packaged (plugins) and governed (config)?
  • These layers compose. Understanding each one — and where its boundaries are — is the difference between a demo and a dependable system.

The stack at a glance

Seven layers, bottom to top

6 · Plugins — packaged bundles of everything below, shared as one installdistribution
5 · Skills — procedural knowledge loaded on demandknow-how

2 · Tools — structured actions the model can invokecapability
1 · Context window — everything the model can see at oncefoundation

01 / 07

Context Windows

The model's entire working memory — and the single hardest constraint in AI engineering.

Context · Definition

The context window is everything the model sees in one pass

  • One request, one window. System prompt, conversation history, tool results, files — all of it flattens into a single token sequence the model reads before producing output.
  • Nothing outside it exists. The model has no hidden database of your conversation. If a fact isn't in the window (or in the weights), the model doesn't know it.
  • It's working memory, not storage. Persistent memory is something you build on top — by writing things into future windows.

Every technique in this deck is, at bottom, an answer to one question: what should be in the window right now?

Context · Tokens

Tokens are the unit of everything

  • Models read tokens, not characters. A token is a common chunk of text — roughly 3–4 characters of English, or about ¾ of a word.
  • Everything is metered in tokens: window size, API pricing, rate limits, latency. "200K context" means 200,000 tokens — about 500 pages of text or a mid-sized codebase.
  • Code and non-English text tokenize worse. Whitespace-heavy code, CJK languages, and base64 blobs consume far more tokens per character than English prose.
// "The quick brown fox jumps over the lazy dog"
["The", " quick", " brown", " fox", " jumps", " over", " the", " lazy", " dog"]
// 9 tokens · 43 characters · ≈ 4.8 chars per token

Context · Composition

What actually fills the window

In an agent session, your prompt is a sliver. A typical mid-session breakdown:

System prompt & harness instructions~5%
Tool definitions (schemas for every available tool)~10%
Tool results — file contents, command output, search hits~60%
Conversation history & model reasoning~20%
Your actual messages~5%

Implication: the biggest lever on context health isn't shorter prompts — it's controlling what tools dump into the window.

Context · Scale

Windows grew ~250× in four years

2020 · GPT-32K tokens · a long email
2023 · GPT-4, Claude 28K–100K · a paper, a novella
2024–25 · Claude 3/4 era200K standard · a codebase
2025–26 · frontier1M+ · a monorepo, hours of transcript
  • Qualitative shift: at 200K+ you stop summarizing inputs and start dropping whole artifacts in — full files, full logs, full documents.
  • But growth didn't repeal the economics — which is the next slide.

Context · The catch

Bigger windows aren't free

  • Cost scales with input. You pay for every token, every turn. A 150K-token conversation re-sends 150K tokens with each new message.
  • Latency scales too. More input tokens means slower time-to-first-token.
  • Attention degrades — "context rot." Retrieval quality isn't uniform across the window; instructions buried mid-window get followed less reliably than ones near the start or end. Long, noisy histories dilute the signal.
  • Stale context misleads. An old file version or a superseded plan sitting in history can be worse than nothing.

Rule of thumb: treat context as a scarce budget with diminishing returns — spend it on what's load-bearing for the next step.

Context · Management

Four strategies for staying inside the budget

1 · Compaction

When the window nears its limit, summarize the conversation and continue with the summary plus recent turns. Claude Code does this automatically.

2 · Retrieval (RAG)

Keep knowledge outside the window; search and pull in only relevant snippets at ask time, instead of carrying everything always.

3 · Subagents

Delegate a noisy task (a broad code search, a log dive) to a separate agent with its own window; only its conclusion returns to yours.

4 · External notes

Write state to files — plans, memory directories, scratchpads — and re-read what's needed. Files are memory that survives the window.

Context · Economics

Prompt caching: pay for the prefix once

  • The observation: in multi-turn use, most of each request is identical to the last one — same system prompt, same tool schemas, same early history.
  • The mechanism: the API caches a processed prefix; subsequent requests that share it skip recomputation. Cache reads cost ~10% of normal input tokens.
  • The design consequence: put stable content first (system prompt, tools, documents) and volatile content last. One changed byte early in the prefix invalidates everything after it.

documents

new turn

02 / 07

Tools

How a text predictor gets hands: structured actions the model can request and your code executes.

Tools · Definition

The model never runs anything. It asks.

  • Tool use is a contract. You describe available functions; the model replies with a structured request — tool name plus JSON arguments — instead of (or alongside) prose.
  • Your code executes. The harness runs the function and feeds the result back as a new message. The model never touches your system directly.
  • This boundary is the safety model. Because execution happens in your code, you can validate, sandbox, log, rate-limit, or refuse any call.

A tool call is a proposal. The harness — and its permission rules — decide whether it becomes an action.

Tools · Anatomy

A tool is a name, a description, and a schema

{
  "name": "get_weather",
  "description": "Get current weather for a location.
      Returns temperature, conditions, and humidity.
      Use when the user asks about weather or outdoor plans.",
  "input_schema": {
    "type": "object",
    "properties": {
      "location": { "type": "string", "description": "City name or lat,lon" },
      "unit":     { "enum": ["celsius", "fahrenheit"] }
    },
    "required": ["location"]
  }
}

The description is a prompt. It's the only thing the model reads to decide when and how to call the tool — write it like documentation for a sharp new teammate.

Tools · The loop

One round-trip of tool use

1 · prompt
"What's the weather in Oslo?"
→
2 · tool_use
model: get_weather({location:"Oslo"})
→
3 · execute
your code calls the API
→
4 · tool_result
{"temp": 6, "cond": "rain"}
→
5 · answer
"6°C and raining — bring a coat."
  • Steps 2–4 can repeat many times before a final answer. That repetition, aimed at a goal, is what we'll later call an agent.
  • Results land in the context window — which is why tool output size is a context-management concern (slide 7).

Tools · Composition

Parallel when independent, chained when dependent

Parallel

The model can emit several tool calls in one turn — read three files at once, run lint and tests together. Halves the wall-clock of independent work.

Chained

Output of one call feeds the next: search for the file → read it → edit it → run the tests. Each step's result shapes the model's next decision.

  • Good harnesses exploit both: batch what's independent, sequence what isn't — and interleave model reasoning between steps to react to failures.

Tools · Design

What separates good tools from bad

  • Few and powerful beats many and narrow. Twenty overlapping tools confuse selection; five orthogonal ones with clear boundaries get chosen correctly.
  • Return signal, not dumps. A search tool that returns 10 relevant snippets beats one that returns 3,000 raw lines — every result token is context budget spent.
  • Errors should teach. "File not found: did you mean src/config.ts?" lets the model self-correct in one step; a bare stack trace wastes a turn.
  • Make misuse hard. Enums over free strings, required fields, sensible defaults. The schema is a guardrail.

Test of a good tool: could a competent human use it correctly from the description alone? The model is in the same position.

Tools · In practice

The tool families inside Claude Code

FamilyToolsWhat it enables
FilesRead · Write · Edit · Glob · GrepNavigate and modify a codebase surgically
ExecutionBash (foreground & background)Build, test, run anything with a CLI
WebWebSearch · WebFetchPull in docs and current information
DelegationAgent (subagents) · WorkflowFan work out to parallel contexts

A general-purpose file+shell+web toolset turns out to cover a remarkable share of knowledge work — which is why the same loop handles coding, research, and ops.

MCP

The Model Context Protocol — an open standard that lets any AI app talk to any data source or service.

MCP · The problem

Before MCP: the N × M integration tax

  • Every AI app × every service = a custom integration. Slack for Claude, Slack for Cursor, Slack for your internal bot — three implementations of the same thing.
  • N apps × M services means N×M connectors, each with its own auth, schema, and bugs. Nobody maintains that matrix for long.
  • The fix is the same as it always is: a protocol. Build to the standard once; interoperate with everything that speaks it.

MCP is to AI integrations what USB-C is to peripherals: one port, any device.

Open-sourced by Anthropic in Nov 2024; since adopted across the industry — N×M becomes N+M.

MCP · Definition

Three roles: host, client, server

HOST
the AI app — Claude Code, Claude.ai, an IDE
→
CLIENT
one connection per server, managed by the host
→
SERVER
wraps a capability: GitHub, Postgres, Slack, your API
  • A server is a small program that exposes what a system can do in a standard, machine-readable form.
  • The host aggregates. Connect five servers and the model sees one unified tool list — it neither knows nor cares where each tool lives.
  • Anyone can publish a server — vendors ship official ones; thousands of community servers exist for databases, browsers, clouds, and SaaS tools.

MCP · Architecture

One host, many worlds

Claude (model) — sees one merged tool list
Host app: routes calls, enforces permissions
github server
postgres server
browser server
internal-api server
  • Tools namespace automatically (e.g. mcp__github__create_pr), so servers can't collide.
  • Permissions apply at the host, uniformly — a server only gets invoked when the harness allows that call.

MCP · Primitives

Servers can offer three kinds of things

PrimitiveDirectionMeaningExample
Toolsmodel-controlledActions the model may invokecreate_issue, run_query
Resourcesapp-controlledData the host can attach as contexta file, a schema, a dashboard
Promptsuser-controlledReusable templates a user invokesa "summarize PR" command
  • Tools dominate in practice — most servers are effectively tool collections — but the three-way split keeps who-decides-what explicit.

MCP · Transports

Local process or remote service

stdio — local

The host spawns the server as a child process and speaks JSON-RPC over stdin/stdout. Zero network setup; full access to your machine. Right for filesystem, git, local browsers.

Streamable HTTP — remote

The server runs as a web service; auth via OAuth. Right for SaaS integrations — one hosted server, many users, no local install.

# wiring servers into Claude Code
claude mcp add github -- npx -y @modelcontextprotocol/server-github
claude mcp add --transport http linear https://mcp.linear.app/mcp

MCP · Caution

A server is code you're trusting

  • Servers run with real credentials — your GitHub token, your database. Install from sources you trust, exactly as you would any dependency.
  • Tool results are untrusted input. A web page or ticket fetched through MCP can contain adversarial text ("ignore your instructions and…"). Prompt injection enters through data, not just prompts.
  • Every server spends context. Each connected server adds tool schemas to the window; a host with tool-search loads them on demand instead. Connect what you use.
  • Scope with permissions. Allow the read tools broadly, gate the write tools — the config layer (section 07) is where this lands.

04 / 07

Agents

What you get when a model, tools, and a loop meet a goal — and the patterns that make autonomy dependable.

Agents · Definition

Agent = model + tools + loop, aimed at a goal

  • The defining trait is who decides. An agent chooses its own next step from what it just observed — which file to open, whether to re-run the tests, when it's done.
  • Chat answers; agents accomplish. "Fix the failing CI build" ends not with an explanation but with a green build — after reading logs, editing code, and re-running checks.
  • Autonomy is a dial, not a switch: from single tool call, to human-approves-each-step, to hours of unattended work.

An agent is a model using tools in a loop, where the model's own output decides the next iteration.

Agents · Spectrum

Workflows vs agents: who owns the control flow?

Workflow — code decides

Fixed steps you author: classify → route → draft → review. Predictable, testable, cheap. Right when the path is known in advance.

Agent — model decides

The model plans and adapts as it observes. Right for open-ended tasks — debugging, research — where the path can't be scripted.

  • Best systems are hybrids: deterministic scaffolding (a script that fans out work, a required verify stage) around agentic steps where judgment is needed.
  • Start with the simplest thing that works. Reach for full autonomy only when a workflow can't express the task.

Agents · The loop

Gather context → act → verify → repeat

gather
read files, search, ask
→
plan
decide the next step
→
act
edit, run, call APIs
→
verify
tests, lint, re-read the diff
↺
  • Verification is what makes agents work. Environments with checkable feedback — tests, compilers, linters — let the agent catch and fix its own mistakes. That's why coding was the first domain agents cracked.
  • No feedback signal, no reliability. If success can't be checked, the loop degrades to hoping the first attempt was right.

Agents · Delegation

Subagents: fresh windows for messy work

  • The mechanism: an agent spawns another agent with its own context window, gives it a task, and receives only the final report back.
  • Why it matters for context: a search that touches 40 files burns tens of thousands of tokens — in the subagent's window. The orchestrator keeps the one-paragraph conclusion.
  • Why it matters for speed: independent subagents run in parallel — five reviewers over five modules at once.
  • Specialization: subagents can carry their own system prompt, model tier, and restricted tool set (a read-only "explorer", a test-runner).

Rule of thumb: delegate when the work's process is noisy but its result is compact.

Agents · Patterns

Multi-agent shapes that recur

PatternShapeUse when
Orchestratorone lead plans, workers execute in paralleldivisible work: audits, migrations, sweeps
Pipelineeach item flows through stages independentlymany items × several steps, no cross-item deps
Judge panelN independent attempts, then scoring & synthesiswide solution spaces: design, naming, strategy
Adversarial verifyskeptic agents try to refute each findingkilling plausible-but-wrong results before you act

Cost note: multi-agent runs multiply tokens. Reach for these when coverage or confidence genuinely needs them, not by default.

Agents · Memory

Long horizons need memory beyond the window

  • Within a session — compaction: summarize the transcript as it grows so work continues past the window limit (section 01's strategies, applied automatically).
  • Across steps — working files: agents that write plans and progress notes to disk survive interruptions and stay on track; the file is the source of truth, not the transcript.
  • Across sessions — persistent memory: a directory of small fact files (who the user is, project conventions, feedback received) reloaded at startup. Memory becomes an editable artifact, not a black box.
  • Curation beats accumulation: stale memory misleads exactly like stale context. Update and delete, don't just append.

Agents · Safety

Guardrails: trust is earned per action, not per agent

  • Permission gates: reads flow freely; writes, pushes, and deletes require rules or a human. The gate lives in the harness, outside the model's control.
  • Sandboxing: risky execution happens in containers, worktrees, or restricted shells — blast radius by construction, not by promise.
  • Reversibility bias: prefer branches over main, staged rollouts over big-bang, dry-runs before real runs. Cheap undo makes autonomy affordable.
  • Evaluation: agents are stochastic — measure end-to-end task success across runs, not single demos. Evals are to agents what tests are to code.

05 / 07

Skills

Procedural knowledge in a folder: how an agent learns your way of doing things — without spending context until it's needed.

Skills · Definition

A skill is a folder with instructions inside

  • At its core: a directory with a SKILL.md file — instructions for a specific kind of task, plus optional scripts, templates, and reference docs alongside.
  • Loaded on demand. The agent sees only each skill's name and one-line description; when a task matches, it reads the full instructions into context and follows them.
  • Knowledge, not capability. Tools give an agent the ability to act; skills tell it how your team wants it done — the deploy runbook, the brand rules, the review checklist.

Tools are the hands. Skills are the training: expertise on paper, read just-in-time.

Skills · Anatomy

SKILL.md: frontmatter for triggering, body for doing

my-plugin/skills/deploy-checklist/
├── SKILL.md          ← the entry point
├── rollback.sh       ← helper the skill can run
└── reference.md      ← details, read only if needed

---
name: deploy-checklist
description: Safe production deploy steps. Use when the user
  asks to deploy, release, or ship to production.
---
## Steps
1. Run the full test suite; abort on any failure.
2. Check current on-call in #ops before proceeding. ...

The description is the trigger. It's the only part always in context — it must say both what the skill does and when to use it.

Skills · Mechanism

Progressive disclosure: three levels of loading

Level 1 · Metadata — name + description of every skill, always in context~50 tokens each
Level 2 · SKILL.md body — full instructions, loaded when the task matches~500–5K tokens
Level 3 · Bundled resources — scripts, templates, reference docs, read only if the work requires themunbounded
  • This is context economics again: you can install a hundred skills and pay only for the ones a task actually invokes.
  • Scripts beat prose for determinism: a bundled script runs the same way every time — better than asking the model to improvise the same 12 shell commands.

Skills · Boundaries

Skill, tool, or MCP server?

You need…Reach forBecause
A new capabilityTool / MCP serverThe agent literally can't do it today (query prod DB, call your API)
A procedure done your waySkillThe agent could fumble through; the skill makes it reliable and yours
BothMCP + skillMCP provides access; the skill encodes how to use it well
Always-on factsCLAUDE.md (section 07)Small, universal context that should load every session

Litmus test: "it can't" → tool. "it can, but inconsistently" → skill.

Skills · Craft

Writing skills that actually fire and actually help

  • Tune the description for triggering. Include the verbs and nouns users actually say ("deploy", "release", "ship"). A skill that never fires is dead weight; one that overfires pollutes unrelated tasks.
  • Write for a capable reader. State the non-obvious: constraints, order, failure modes. Skip what any competent agent already knows.
  • One skill, one job. A skill that covers everything matches nothing. Split by task, not by team.
  • Evaluate like software. Run representative prompts with and without the skill; keep only what measurably changes behavior. Tooling like skill-creator scaffolds and benchmarks this.

06 / 07

Plugins

The distribution layer: skills, agents, commands, hooks, and MCP servers, packaged as one installable unit.

Plugins · Definition

A plugin bundles the other layers into one install

  • The problem it solves: a useful setup is scattered — three skills here, an MCP server there, a custom agent, two hooks. Sharing that piecemeal doesn't survive contact with a team.
  • A plugin is the package: one versioned directory carrying any mix of skills, slash commands, subagent definitions, MCP server configs, and hooks.
  • One install, whole capability. "Our release toolkit" becomes a single name a teammate adds — not a wiki page of setup steps.

Skills teach. MCP connects. Agents specialize. A plugin is how all of that ships.

Plugins · Anatomy

Inside a plugin directory

release-toolkit/
├── .claude-plugin/
│   └── plugin.json      ← name, version, description
├── commands/            ← slash commands (/release, /hotfix)
├── skills/              ← procedures (changelog style, deploy steps)
├── agents/              ← specialized subagents (release-reviewer)
├── hooks/
│   └── hooks.json       ← e.g. block direct pushes to main
└── .mcp.json            ← MCP servers this plugin needs (CI, Sentry)
  • Every part is optional — a plugin can be a single skill or a full toolkit.
  • Components behave exactly as if installed individually; the plugin is packaging, not a new runtime.

Plugins · Distribution

Marketplaces are just git repos

# add a marketplace (any git repo with a marketplace manifest)
/plugin marketplace add acme-corp/claude-plugins

# then browse & install from it
/plugin install release-toolkit@acme-corp
  • No central store required. A marketplace is a repo with a manifest listing plugins — your org can run a private one next to public community ones.
  • Teams pin plugins in project config, so cloning the repo and starting Claude yields the same toolkit for everyone — capabilities as code.
  • Same trust rule as MCP: a plugin executes with your permissions. Review what you install; prefer sources you'd accept a dependency from.

Plugins · When

When a plugin is the right container

  • The same setup keeps getting rebuilt. If a workflow's skills and servers are being copy-pasted between people or repos, that's a plugin asking to exist.
  • You want a workflow standardized, not just available — the plugin's hooks and commands make the right way the easy way.
  • You maintain a product others integrate with: shipping an official plugin beats every team writing its own glue.
  • Not yet worth it: a single personal skill or one MCP server — install those directly and skip the packaging until sharing demands it.

Claude Config

The governance layer: settings, memory files, permissions, and hooks that decide how all the other layers behave.

Config · Settings

Settings cascade: enterprise → project → user

Managed policy — org-enforced, can't be overriddenhighest
.claude/settings.local.json — your personal per-project tweaks (gitignored)↑
.claude/settings.json — the project's shared, committed settings↑
~/.claude/settings.json — your defaults across all projectsbase
  • More specific wins. Permissions, env vars, hooks, and model choice merge down this chain.
  • Committed project settings are the team lever: one file makes every teammate's Claude behave consistently in this repo.

Config · Memory files

CLAUDE.md: standing instructions, loaded every session

  • What it is: a Markdown file of instructions and facts injected into context at startup — build commands, conventions, hard rules ("never disable a CI check").
  • Where it lives: ~/.claude/CLAUDE.md for personal global rules; repo-root CLAUDE.md for the project; subdirectory files for area-specific guidance.
  • It spends context every single session — that's its power and its cost. Keep it to what's always relevant; push occasional procedures into skills (level-loaded) instead.
  • Auto-memory complements it: Claude can maintain its own directory of small fact files across sessions — learned preferences and project state, indexed and editable.

Config · Permissions

Permissions: allow, ask, deny — per tool, per pattern

{
  "permissions": {
    "allow": ["Bash(npm test:*)", "Bash(git diff:*)", "Read(**)"],
    "ask":   ["Bash(git push:*)"],
    "deny":  ["Read(.env*)", "Bash(rm -rf:*)"]
  }
}
  • Rules are patterns over tool calls — command prefixes, file globs, MCP tool names. Deny always beats allow.
  • Modes set the day's stance: normal (ask for unknowns), plan mode (read-only until a plan is approved), auto-accept edits, sandboxed bash — autonomy tuned to risk.

Config · Hooks & environment

Hooks make behavior guaranteed, not requested

  • Hooks are your scripts on harness events — PreToolUse, PostToolUse, Stop, and more. A hook can block a tool call, reformat a file after every edit, or notify you when a run finishes.
  • The key property: hooks are enforced by the harness, not remembered by the model. "Always run the formatter" as a hook is a guarantee; as a prompt line it's a hope.
  • The rest of the surface: env vars per project, default model selection, output styles, status line, keybindings — plus slash commands as user-invoked entry points into all of it.

Pattern: anything phrased "every time X, do Y" belongs in a hook, not in a prompt.

Closing

The stack, assembled

  • Context is the budget — every other layer exists partly to spend it well.
  • Tools give capability; MCP standardizes where they come from.
  • Agents are tools-in-a-loop with verification — trustworthy exactly to the degree their work can be checked and their permissions are scoped.
  • Skills load know-how on demand; plugins ship it; config governs it.

Build the smallest thing that works, verify relentlessly, and let the model decide only what code can't. The rest is context engineering.
